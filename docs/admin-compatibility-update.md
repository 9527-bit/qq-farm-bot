# 多用户管理兼容修复与部署检查

## 修复范围

合并提交 `4e0259c` 纳入了上游的单管理员免登录改造，虽保留了本地提交历史，
但没有保留完整的多用户管理行为。不要把该提交直接用于原有的多用户生产部署。

本修复恢复用户数据库登录、后台用户/卡密/登录日志管理、密码修改、会话校验和账号隔离。
普通用户只能操作自己的农场，管理员可使用管理接口；新版宠物入口和账号设置布局继续保留。
微信登录继续使用上游的内置协议，不恢复前端对已移除配置加载方法的调用。
原有微信兼容配置保留用于数据兼容，但不改变新版内置扫码协议；账号隔离始终启用。
旧版内置的固定超级管理员凭据不再接受，现有数据库管理员不受影响。
旧 `users-with-password` 接口仅作为管理员用户列表的兼容别名，不返回密码或哈希。

健康检查使用无需认证的 `http://127.0.0.1:3007/api/health`。
不要使用需要用户会话的 `/api/status`，也不要仅为健康检查开放业务接口。

## 上线前

1. 确认修复已提交并推送，记录待部署的提交号，不能仍是 `4e0259c`。
2. 在干净环境执行 `pnpm install --frozen-lockfile`、`pnpm -C core test` 和 `pnpm build:web`。
3. 确认服务器实际挂载目录、当前容器镜像 ID、Compose 项目名和对外端口。
4. 保存当前代码提交号、未提交补丁、Compose 文件和 `.env`；敏感备份不得公开。
5. 为正在运行的容器对应的镜像 ID 创建独立备份标签，不能只假定 `latest` 就是运行版本。
6. 与使用者确认停机窗口后，停止容器再备份完整数据目录，避免文件写入期间的不一致备份。

对于本次服务器，已确认：

- 项目目录：`/root/farm/qq-farm-bot`。
- 数据目录：`/root/farm/data`，挂载到 `/app/core/data`。
- 面板端口：`9528:3007`，不能被仓库默认的 `3007:3007` 覆盖。
- 服务器原有两个微信登录文件与 `4e0259c` 对应文件一致；后续更新仍应重新比较。
- 代码、配置和旧镜像已有备份，但必须另外完成一致的数据备份。

## 构建和切换

保留服务器自己的端口映射、环境变量和挂载路径，只把健康检查目标改为上面的健康接口。
可在同级候选目录构建新代码，避免覆盖运行目录内的本地修改。
候选版本构建成功之前不要删除旧容器或旧镜像，不要同时启动两套服务访问同一个数据目录。
切换时保持 Compose 项目身份一致，或先停止并移除旧容器再启动新容器，避免固定容器名冲突。
不要使用 `down -v`，不要删除或重建数据目录。

启动后检查健康状态、容器日志及 9528 端口，并分别验证管理员和普通用户登录：
用户数据与账号数保持不变，普通用户不能查看其他人的农场或管理接口，管理员后台可打开。
真实账号的扫码、自动化和游戏服务连通性仍需在部署后验证；本地回归测试不替代这些验证。

## 回退

发生问题时先停止新容器，保存其日志和失败后的数据副本。
恢复备份 Compose 配置，并明确使用记录的旧镜像标签，不能继续使用已被新构建覆盖的 `latest`。
若新版本已改写数据，应结合停机备份评估恢复，避免旧程序读取不兼容数据；
恢复备份会丢失备份之后的变更，必须确认后再执行。
